# 产品形态与分发策略

> 状态：规划（2026-10-20）。与《3D重构开发计划》配合阅读：那份讲"做什么内容"，这份讲"以什么形态交付给谁"。

## 1. 先拆前提：实用性瓶颈不在浏览器

判断一款产品是否实用，不看它跑在什么容器里，看两件事：**环境确定性**与**入口确定性**。浏览器恰好在两点上都弱，但弱的方式很具体：

| 真实痛点 | 严重度 | 具体表现 | 现状 |
|---|---|---|---|
| 机房浏览器不可控 | ★★★ | 360、QQ 等双核浏览器 WebGL 支持参差，部分默认关闭硬件加速，部分对 ES 模块解析异常 → 三维场景黑屏 | **仍在**：只能靠启动器固定用 Edge/Chrome 开窗口来规避 |
| 双击 `index.html` 打不开 3D | ★★★ | ES 模块受 CORS 限制，只能退到二维版。评委/老师双击看到的不是三维场景 | **已解决**：双击 `桥见柳州.exe` 自带 HTTP 服务 |
| 启动依赖本机 Node.js | ★★★ | 现版 `start.bat` 调用 `node server.js`，机房与展馆电脑通常没有安装 Node，启动直接失败 | **已解决**：启动器内置静态服务，不需要 Node |
| 没有软件感 | ★★ | 无图标、弹黑窗口、无独立窗口，展陈与课堂场景显得业余 | **已解决**：Edge/Chrome `--app` 独立窗口，无地址栏无标签页 |
| 移动端不可用 | ★★★ | 当前移动端整体回落二维版，而学生真正持有的设备是手机 | **已解决**：三维在移动端可用（触摸环视、双指缩放、底部抽屉） |

排名即优先级：**环境确定性 > 入口 > 软件感**。"原生"只能改善前两条，改善不了第三条——手机上没有"原生桌面应用"这回事。

因此打包的正当理由是"把运行环境固定下来"，而不是"看起来更专业"。这个区别直接决定选型。

## 2. 封装方案评估

| 方案 | 体积 | 优势 | 致命伤 |
|---|---|---|---|
| **Electron** | 百 MB 级 | 运行环境完全可控，现有代码零改动，双平台成熟 | 体积大、内存高、Windows 未签名弹 SmartScreen 警告、需与上游版本同步 |
| **Tauri v2** | 3–10 MB | 小、启动快、系统集成好 | 依赖系统 WebView2 / WebKitGTK；**Linux 的 WebKitGTK 跑 WebGL 重场景历史上不稳**，等于引入我们正要消除的不确定性 |
| **PWA** | 0 | 可安装、有图标、可离线 | 首次安装需联网；系统集成浅；Firefox/Safari 不支持；**解决不了机房浏览器差异** |
| **单文件启动器** | 2–3 MB | 自带静态服务、免 Node、双击即用、可交叉编译双平台 | 仍依赖系统 Chromium（但可检测并给出明确提示） |

**结论：采用单文件启动器，Electron 仅作为赛后可选项。**

排除 Tauri 的理由是把不确定性引进来；排除 PWA 的理由是它改善入口却不改善环境确定性，恰好解决错了问题。

## 3. 场景决定形态：一个内核，四种外壳

教育产品不存在一种形态打天下。按真实使用场景拆：

| 场景 | 使用者 | 关键约束 | 形态 | 改造成本 |
|---|---|---|---|---|
| A 课堂 | 教师主导 | 40 分钟、投屏、断网、5 分钟讲完一个知识点 | 投屏模式 `?present=1`（✅ 已实现） | 已完成 |
| B 科技馆 / 研学 | 陌生观众 | 无人指导、15 分钟、超时复位 | Kiosk 模式 `?kiosk=1`（✅ 已实现，巡览总览 + 五座桥） | 已完成 |
| C 学生随身 | 学生本人 | 微信可开、首屏 3 秒内、不装东西 | 移动端轻量版（预渲染帧） | 2–3 天 |
| D 电脑自学 | 教师 / 学生 | 双击即用、无 Node、环境可控 | 单文件启动器 `桥见柳州.exe`（✅ 已实现，10.5 KB） | 已完成 |

现有架构（纯静态、零依赖、hash 路由、可降级）恰好支持这种拆分——这是早期技术选择的红利，不需要重构。

## 4. 各形态的实现要点

### 4.1 单文件启动器（P0）

**现状**：已实现。`launcher/Program.cs`（C#，约 10 KB）由 `tools/build-launcher.mjs` 调用系统自带的 .NET Framework `csc` 编译成 `桥见柳州.exe`（10.5 KB），不下载任何依赖。
内置 `TcpListener` 静态服务（不用 `HttpListener`——它对 `127.0.0.1` 前缀需要 URL ACL 授权，普通用户会失败），从 4173 起自动挑端口；再用系统 Edge/Chrome 的 `--app` 模式开独立窗口，窗口关闭即停服务。
**平台边界**：exe 仅 Windows；Linux 仍用 `start.sh`（需 Node.js 18+）。

**做法**：用 Go（约 300 行）编译单文件可执行程序：

1. `embed.FS` 内嵌全部静态资源（含 `vendor/three/`）
2. `net/http` 起本地服务，端口从 4173 起自动探测可用端口
3. 探测系统 Chromium：Windows 依次找 Edge（注册表/默认路径）→ Chrome；Linux 找 `google-chrome` / `chromium`
4. 以 `--app=http://127.0.0.1:PORT/#atlas --window-size=1440,900` 启动（无地址栏、无标签页，观感即原生应用）
5. 浏览器窗口关闭 → 服务退出，不在后台驻留
6. 找不到 Chromium 时给出可读提示，而非黑屏

`go build` 交叉编译出 `bridge-windows-amd64.exe` 与 `bridge-linux-amd64`，共约 5 MB。

同时保留现有 `start.bat` / `start.sh` 作为"已装 Node"环境的备用路径。

### 4.2 投屏模式（P1）

- 入口参数 `?present=1`：HUD 字号 ×1.25、提高对比度、隐藏次要按钮、按 16:9 安全区排版
- 不依赖 hover（投屏时鼠标不靠近）→ 所有 hover 反馈都要有等价的可点击表达
- 键盘快捷键：`0` 回总览、`1–5` 切桥、`Esc` 复位
- 讲解节奏：每个视角切换控制在一次点击内

### 4.3 Kiosk 模式（P1）

- 入口参数 `?kiosk=1`：隐藏导航、全屏、禁用右键菜单
- 自动巡航：每 8 秒在"五桥 + 两馆"之间轮转，复用现有 `focusOn`
- 任意 `pointerdown` / `keydown` → 停止巡航、交出控制权
- 60 秒无操作 → `resetView()` + 恢复巡航
- **ODbL 署名必须保留**，不得因 Kiosk 而隐藏

### 4.4 移动端轻量版（P2）

不做 3D 移植，改做"随身复习载体"：

- 构建期离线预渲染 24–36 帧环绕图（WebP，每帧 30–60 KB）
- 移动端以 `<img>` 序列 + pointer 手势同步帧实现"伪旋转"，零 WebGL 依赖
- 结构卡片：桥型、关键构件、力流箭头动画（CSS/SVG）
- 知识挑战做成可滑动卡片流，带错题回顾
- 首屏不加载 three.js，目标 3 秒内出内容

预渲染帧方案同时规避了安卓低端机 WebGL 发热掉帧、竖屏视野过窄、触摸旋转与页面滚动冲突三个问题。

## 5. 移动端：该做与不该做

**该做**：把手机当作"看结构、背概念、刷题"的轻量端。

**不该做**：把 `atlas.mjs` 的几何原样塞进手机。低端安卓大场景 WebGL 会发热掉帧；竖屏视野只有横向一半；为手机重写一套渲染，工作量远大于收益。

若确需在手机上保留可旋转的三维观感，正确路径是预渲染序列帧，而非实时渲染。

## 6. 路线与优先级

| 优先级 | 动作 | 成本 | 解锁什么 |
|---|---|---|---|
| **P0** | 单文件启动器（免 Node、双击即用） | 1 天 | 机房、展馆、评委三处入口全部打通 |
| **P0** | M2 文惠桥垂直切片 | 3–4 天 | 教学闭环；这是内容侧唯一真正的瓶颈 |
| P1 | Kiosk 巡航模式 | 0.5 天 | 科技馆 / 研学场景 |
| P1 | 投屏模式 `?present=1` | 0.5 天 | 课堂场景 |
| P2 | 移动端轻量版 | 2–3 天 | 学生随身场景 |
| P3 | Electron 便携包（**放 Release，不进仓库**） | 2 天 | 环境完全确定（仅 Windows） |

判断依据：**内容的完成度决定产品价值，外壳只决定触达率。** 先用 P0 把"双击能进、断网能跑"这条底线焊死，再用 M2 让产品第一次讲清一个知识点。

## 7. 明确不做

- **Tauri**：Linux WebKitGTK 的 WebGL 不确定性，与"消除环境不确定性"的目标相反
- **原生重写**：成本远超收益，且现有 Web 技术栈是跨形态复用的基础
- **PWA 安装**：解决错了问题，且首次安装依赖联网
- **应用商店上架**：学生团队维护成本过高，且不解决实际触达
- **为移动端重写 3D**：见第 5 节

## 8. 与现有架构的关系

当前几条设计在拆分时直接受益，应继续保持：

- 纯静态、零后端 → 可以内嵌进任何外壳
- 零依赖（three.js 本地内置）→ 启动器只需 `embed`，不需包管理器
- hash 路由 → 桌面、Kiosk、移动端可用同一份页面，只靠入口参数区分形态
- 三维不可用即回落二维 → 移动端与老旧机房都有保底体验

## 9. 风险与待确认

- **赛事作品包体积限制未知**：需先确认上限，它直接决定 Electron 方案是否可行（百 MB 级很可能超标）
- **预渲染帧需要可运行 Chromium 的环境生成**：当前开发沙箱无法运行 Chromium，需另找环境离线生成后再入库
- **Linux 桌面端实测未做**：三维渲染与启动器均需在目标环境各跑一次
- **启动器与 `server.js` 的端口逻辑需合并**：两边都做端口探测会造成行为不一致
